Les deux pilotes explorateurs ont été essayés pour de vrai le 2026-10-06 sur un dépôt jouet (hors corpus) avec le `execute_driver` du lanceur, avec l'autorisation du mainteneur : ils sont `verified: true`, preuves dans [`pat-19-preflight-v2-2026-10-06.json`](pat-19-preflight-v2-2026-10-06.json). **Les noms d'outils ont été corrigés par cet essai, avant le gel** : `omp` 18.6.1 a refusé `--tools=read,grep,find,ls` (« Unknown tool in --tools: ls » ; `find` indisponible dans la session) ; l'argv gelé est `--tools=read,grep,glob`, le même trio que l'explorateur cloud (Read/Grep/Glob). L'intention validée par le mainteneur (lecture seule) est inchangée ; le chargeur n'accepte que `read`, `grep`, `glob`.

## 1. Question posée

Pour des correctifs bornés de ce dépôt, un rapport d'exploration produit **avant** le travail par un explorateur en lecture seule (a) localise-t-il les bonnes **fonctions** (métrique principale) et les bons fichiers (tamis local, sans cloud), puis (b) réduit-il le coût premium **par tâche acceptée** d'un implémenteur cloud, à acceptation au moins égale (comparaison) ?

## 4. Juge de localisation (déterministe, sans modèle ni réseau)

La vérité terrain de chaque tâche vient du **diff fusionné** (snapshot et SHAs du manifeste), calculée par `foundry.local_first_exploration.ground_truth` :

- **fichiers produit** : fichiers modifiés ou supprimés par le diff, sous les préfixes produit du juge de la v1 (`SOURCE_PREFIXES` : `plugins/foundry/tooling/` et `plugins/foundry/hooks/`), hors `tests/` et hors documentation (`_is_doc` : `.md`, `.json`, `.txt`, `docs/`). C'est la classification que le juge de la v1 utilise déjà, pas une nouvelle. Les fichiers **ajoutés** par le diff ne comptent pas dans le rappel (un explorateur ne peut pas trouver ce qui n'existe pas) mais sont acceptés par la précision ;
- **tous les fichiers du diff** (`all_changed_files`) : chaque chemin que le diff fusionné touche, produit ou non (tests, docs, CHANGELOG compris). Un fichier rapporté est **correct pour la précision** quand le diff l'a réellement modifié ou créé, produit ou non ; le rappel n'utilise que les fichiers et fonctions produit ;
- **fonctions** : pour un fichier Python modifié, les fonctions et méthodes (`f` ou `Classe.methode`, classes imbriquées pointées ; une fonction imbriquée appartient à sa fonction englobante) qui **enveloppent une ligne modifiée** (`git diff -U0` ; une ligne supprimée ou remplacée est lue dans le source de base, une ligne ajoutée ou remplacée dans le source fusionné ; une suppression pure ne s'accroche pas à la ligne voisine : une fonction entièrement supprimée est vraie, sa voisine non) et existent au SHA de base. L'algorithme de diff (myers), l'heuristique d'indentation et les renommages sont **épinglés** : la vérité terrain ne dépend pas de la configuration git de l'utilisateur. Une ligne hors de toute fonction (niveau module) ne donne que le fichier ; un fichier non Python est jugé au niveau du fichier seulement. Les fonctions qui n'existent pas au SHA de base (nouvelles) ne comptent pas dans le rappel de fonctions.

Mesures par tâche : **rappel de fonctions** (**métrique principale du tamis** : vraies fonctions trouvées / vraies fonctions ; voir la section 5), **rappel de fichiers** (mesuré et rapporté, ne décide plus : fichiers vrais trouvés / fichiers vrais), **précision de fichiers** (fichiers rapportés que le diff a réellement modifiés ou créés, produit ou non / fichiers rapportés ; 0 pour un rapport sans fichier). **Plafond de fonctions** : seules les **10 premières** fonctions du rapport comptent pour le rappel de fonctions (11e correcte : non comptée ; un rapport qui énumère toutes les fonctions du fichier n'est noté que sur ses 10 premières). Le rappel de fonctions est indéfini, non nul, quand le diff ne touche aucune fonction (la tâche est alors exclue de sa moyenne : aucune des 12 tâches n'est dans ce cas) ; un nom rapporté correspond au nom qualifié ou à son dernier composant, dans le même fichier). Un rapport absent, illisible ou de mauvais type vaut 0 partout. La vérité terrain des 12 tâches est versée dans [`pat-19-exploration-truth-v2.json`](pat-19-exploration-truth-v2.json) (non vide pour chacune, testé sur les vrais diffs fusionnés). **C'est la source unique du lanceur** : son sha256 est consigné dans la configuration (`exploration.ground_truth`), et le chargement de la configuration refuse (code 2, avant toute tentative) un fichier différent. Les tests la recalculent à partir des diffs fusionnés quand l'historique est présent (ils sont **ignorés avec un message explicite** dans un clone sans l'historique, ou en échec si `PAT19_REQUIRE_TRUTH_HISTORY` est défini).

## 5. Tamis local v2 (sans cloud, règle fixée d'avance)

Chaque candidat explore chacune des 6 tâches du tamis, une tentative bornée (10 min, 25 étapes), jugée sur la localisation. Le préflight machine, contrôle de machine dédiée compris, est refait avant chaque tâche. Aucune exécution cloud n'est possible dans ce mode.

Règle (calculs exacts sur des fractions) :

0. le tamis n'est **complet** que lorsque **les cinq candidats gelés** (`rules.exploration_screening.candidates`, dans cet ordre) ont leurs 6 tâches décidées : un sous-ensemble ne retient jamais un candidat (rapport `incomplete_screening`, candidats manquants listés) et `compare-exploration` refuse un tamis incomplet ;
1. sont éligibles les candidats dont la **précision moyenne de fichiers est ≥ 0,5** (précision au sens large ci-dessus) ;
2. le meilleur rappel moyen de fonctions (**métrique principale**) est comparé au seuil **avant** le départage : s'il est **< 0,5**, ARRÊT (une égalité sous le seuil est aussi un arrêt) ; sinon est retenu l'éligible de rappel moyen de fonctions le plus élevé sur les 6 tâches ; à égalité, la **durée totale la plus courte** ; à égalité de durée, le **candidat listé en premier dans l'ordre gelé** de la configuration (aucun choix ne reste après les résultats) ;
3. **ARRÊT sur « conserver le cloud »** si aucun candidat n'atteint la précision 0,5, ou si le rappel moyen de fonctions du candidat retenu est **< 0,5** (0,5 inclus : exactement 0,5 est retenu). Le rappel de fichiers reste mesuré et rapporté mais ne décide plus.

**Pourquoi le rappel de fonctions décide (décision du mainteneur du 2026-10-06, avant le gel, après lecture de la vérité terrain).** Chaque tâche a un seul fichier produit et 5 des 6 tâches du tamis partagent `trackers/linear.py` : le rappel de fichiers est quasi trivial (citer `linear.py` suffit) et ne départagerait pas les candidats. Un candidat de rappel de fichiers parfait et de rappel de fonctions nul n'est donc **pas** retenu face à un candidat de rappel de fonctions positif. Une tâche dont la vérité terrain n'a aucune fonction est exclue de la moyenne (aucune aujourd'hui) ; si aucune tâche n'a de fonction, aucun candidat n'est retenu (`no_function_in_the_ground_truth`).

**Tentative contaminée** (règle v2, gelée maintenant et non après les résultats) : elle compte pour **0 sur toutes les mesures** (rappel de fonctions, rappel de fichiers, précision) sur cette tâche ; un rapport refusé de même, et le tamis n'est jamais bloqué par un seul signalement. C'est un écart voulu avec la v1, où une contamination rendait la tâche indécise et le tamis incomplet, **et un écart assumé à « une donnée absente n'est jamais zéro » (PAT-ADR-0015), limité au filtre du tamis** (fixé par le coordinateur, non soumis au mainteneur ; validation demandée dans le rapport de campagne) : la comparaison, elle, garde l'inconnu comme inconnu (économie `unavailable`, jamais zéro). **Une exploration coupée par une borne (temps ou étapes) est un refus** (score 0, décidée, jamais rejouée), même si un brouillon JSON figure dans un message ; le prompt annonce les bornes (10 minutes, 25 étapes) et demande de répondre avant de les atteindre. Une exploration dont le budget de temps serait raccourci sous la borne par la fin de l'enveloppe n'est **pas démarrée** (arrêt sur plafond, jamais notée comme refus du modèle). La contamination reste consignée (`report.contaminated`). Une tentative cassée par le lanceur ou interrompue avant le jugement reste, comme en v1, nulle (rejouée une fois) ; une tentative qui a reçu un verdict n'est jamais rejouée.

Aucun candidat n'est retenu tant que chacun n'a pas un enregistrement décidé pour chaque tâche (`incomplete_screening`).

**Tamis qui ne peut plus être complété** (règle du coordinateur du 2026-10-07, avant tout essai du corpus). Une tentative coupée deux fois avant son verdict (ou réglée au registre sans enregistrement) reste indécise pour de bon : la règle de reprise ne la rejoue plus. Quand chaque candidat gelé a toutes ses tâches soit décidées, soit indécises pour de bon, et qu'il en reste au moins une indécise, le tamis ne sera jamais complet : par PAT-ADR-0015 (« une preuve insuffisante conserve le cloud ») la conclusion est **« conserver le cloud » faute de preuve**, aucun candidat n'est retenu, pas de troisième essai sous la v2 (une nouvelle tentative demande une v3). Le rapport l'expose : `exploration_screening.campaign_conclusion: keep_cloud_insufficient_evidence` et `not_completable_tasks` (candidat, PR) ; `selected` reste nul et `compare-exploration` refuse le bras L. Les autres valeurs de `campaign_conclusion` du tamis : `candidate_selected`, `keep_cloud` (arrêt de la règle), `incomplete_screening` (une relance peut encore le compléter).

## 6. Comparaison v2 : A, L, E sur les 6 tâches de comparaison

Chaque tâche est jouée dans les trois bras depuis la même base Git, mêmes critères d'acceptation, même revue.

- **A** : l'implémenteur cloud courant, sans rapport ; juge de tests, revue Opus, au plus 2 corrections (chemin A de la v1) ;
- **L** : comme A, avec le rapport du candidat local retenu **ajouté à l'énoncé** (après le pied d'énoncé du lanceur, dans le TASK.md de l'implémenteur et de ses corrections, jamais dans celui du relecteur ; **seules les 10 premières fonctions** du rapport y figurent, avec les fichiers et la justification, coupés aux limites visibles de la configuration). L'exploration est produite d'abord, localement, **dans la même enveloppe**. Le candidat doit être celui que le tamis a retenu ;
- **E** : comme A, avec le rapport d'un explorateur cloud économique (Haiku 4.5, même rôle en lecture seule, même format de rapport), produit d'abord.

Un explorateur qui ne rend aucun rapport utilisable (refus) laisse l'implémenteur travailler sur l'énoncé simple, le coût de l'explorateur restant compté. Un explorateur contaminé, ou coupé deux fois, laisse le bras indécis sur cette tâche (aucun implémenteur dépensé).

**Métrique** : tokens premium totaux **par tâche acceptée**, explorateur compris : somme non pondérée des quatre classes de tokens facturables (v1) sur tous les modèles ; **Haiku compte comme premium**, les tokens locaux non ; le temps mural local est rapporté (durée de l'exploration locale et durée de chaque bras). Les trois verdicts restent séparés (PAT-ADR-0015) :

- **compatibilité** (L) : critère machine de la v1 (aucun arrêt sur un signal extérieur, swap supplémentaire sous 10 Go) ; `unavailable` si le swap n'est pas mesuré ; E n'a pas de travail local ;
- **qualité** : le taux d'acceptation du bras est **au moins** celui de A sur les mêmes tâches. Les tâches indécises bornent le compte : `pass` seulement si cela tient même au pire, `fail` seulement si cela échoue même au mieux, sinon `unavailable` ;
- **économie** : prime par tâche acceptée du bras **≤ 0,85 × celle de A**. `unavailable` (jamais zéro, jamais une estimation) si une tâche comparée est indécise, si du travail dépensé est inconnu au registre, si un total premium est inconnu ou si un bras n'a accepté aucune tâche.

**Règle** : L est retenu si la qualité **et** l'économie **et** la compatibilité passent, sur les 6 tâches. Une campagne partielle (plafond, panne d'outil, interruption) ne conclut rien (`inconclusive`) : v2 n'a pas d'arrêt séquentiel. Un `fail` sur la campagne complète donne `keep_cloud`. **Une comparaison COMPLÈTE avec un verdict `unavailable` et aucun `fail` est `inconclusive`, et par PAT-ADR-0015 (« une preuve insuffisante conserve le cloud ») la conclusion de la campagne pour cet usage est « conserver le cloud »** : le rapport l'expose (`decision: inconclusive` et `campaign_conclusion: keep_cloud_insufficient_evidence`) ; pas de rejeu, pas de tâche supplémentaire sous la v2 (une nouvelle tentative demande une v3). Les autres conclusions : `retain_local_explorer`, `keep_cloud`, `incomplete_campaign` (campagne partielle : rien n'est conclu). **E contre A** est calculé avec la même règle, à titre **informatif** : il ne produit ni décision ni recommandation. Rien n'est promu (`promotion: false`).

## 7. Enveloppe (FOUNDRY-ADR-0010)

Fichier de l'opérateur, jamais écrit par le lanceur. Les modes v2 sont `screen_exploration` et `compare_exploration`. Valeurs recommandées (consignées en données dans `envelope_recommended` de la configuration), avec leur justification :

| Enveloppe | Plafonds | Pourquoi |
| --- | --- | --- |
| tamis | 0 exécution cloud, 0 token premium, **36 000 s** | 5 candidats × 6 tâches × 10 min au plus = 18 000 s ; le double couvre le rejeu d'une tentative nulle et les préflights |
| comparaison | **120 exécutions cloud**, **60 000 000 tokens premium**, **100 000 s** | par tâche et par bras, au plus 1 implémenteur + 2 corrections et 3 revues = 6 exécutions : 3 bras × 6 tâches × 6 = 108, plus 6 explorations Haiku = 114 ≤ 120 (le plafond tient le pire cas ; le minimum est de 42) ; 60 M = 500 000 par exécution du plafond (la v1 prévoyait environ 444 000 : 20 M pour 45), le volume réel étant inconnu avant mesure : un plafond arrête la campagne, ce n'est pas une estimation ; 100 000 s (27,8 h) couvrent 114 exécutions d'une dizaine de minutes et 6 explorations locales de 10 min, sous la somme des bornes du pire cas |

Le tamis n'utilise aucun cloud. Les plafonds sont cumulés entre lancements (registre) ; une donnée de tokens inconnue arrête les exécutions cloud (`premium_tokens_unmeasurable`).

## 8. Machine dédiée (nouveau contrôle du préflight)

Appliqué par le préflight de `screen-exploration` (avant chaque tâche) et de `compare-exploration` quand le bras L est joué : une fois au départ (avant toute dépense cloud, inscrit au registre avec `phase: "start"`), puis refait **juste avant chaque exploration locale du bras L** (donc après le travail cloud du bras A de la même tâche, pas seulement au début) ; A et E ne chargent aucun modèle local. Quand le lanceur n'a rien écrit au registre depuis le préflight de départ (reprise où le bras A est déjà joué, ou `--paths L`), ce préflight de départ **est** celui qui précède l'exploration : il n'est pas refait deux fois de suite. Commandes en lecture seule déjà autorisées : `ps -axo rss=,command=` et `memory_pressure`. Refus si :

- un processus **hors liste d'autorisation** a plus de **2 Gio** de mémoire résidente (strictement) ;
- le pourcentage de mémoire libre (`System-wide memory free percentage`) est **< 35 %** au départ (**ce critère remplace le seuil « swap de départ » de l'AC d'origine du ticket** : le swap utilisé ne redescend pas sans redémarrage, donc il ne caractérise pas la machine au départ) ;
- une des deux sorties est indisponible (inconnu n'est jamais un succès).

La liste d'autorisation est une donnée de la configuration (`dedicated_machine.allowed_command_patterns`, expressions régulières cherchées dans la ligne de commande) : `lm_studio` (`/LM Studio\.app/`, `/\.lmstudio/`, `lms`), `launcher` (`foundry[._]local_first_runner`, `local_first_runner\.py`), `system` (`/System/Library/`, `/usr/libexec|sbin|bin/`, `/sbin/`, `/Library/Apple/`, `kernel_task`), volontairement étroite : ni `/System/Applications/` (Mail, Photos…) ni `/System/Volumes/Preboot/Cryptexes/App/` (Safari, WebKit) ne sont autorisés, ce sont des consommateurs ordinaires (constat du 2026-10-06 : ChatGPT, OrbStack, Claude, Arc, tous sous `/Applications/`, aucun sous `/System/`). Les valeurs observées (mémoire libre, mémoire résidente par catégorie autorisée, cinq plus gros autres processus **par nom seulement**, jamais un argument de ligne de commande) sont inscrites au registre (entrée `preflight`) et sur chaque enregistrement de tentative (`machine.dedicated`). **Mesure réelle du coordinateur (2026-10-06)** : `preflight --dedicated` avec le plus gros candidat chargé (qwen3.8-27b 6 bits, mémoire résidente de LM Studio 17,9 Gio) lit **51 % de mémoire libre** ; l'application ChatGPT (2,5 Gio) restait ouverte et a été refusée comme prévu par la règle de processus (`dedicated_machine_process_over_2gib:ChatGPT`) ; swap de départ 6,5 Gio. Le seuil de mémoire libre passe donc de 50 % à 35 %, et **la règle de processus est la vraie garde** (elle aurait refusé le processus étranger de 18 Gio de la v1). Mesure consignée dans [`pat-19-preflight-v2-2026-10-06.json`](pat-19-preflight-v2-2026-10-06.json) (`dedicated_machine_measurement`). Limites : le lanceur lancé autrement que par `python3 -m foundry.local_first_runner` n'est pas reconnu comme tel ; la session du coordinateur elle-même (un processus d'agent) peut dépasser 2 Gio et refuser.

## 9. Usage

Depuis `plugins/foundry/tooling`, mêmes arguments que la v1 (`--envelope`, `--state-dir`, `--work-root`, `--repo` : clone complet, `--snapshot`, `--manifest`) :

```
python3 -m foundry.local_first_runner preflight --campaign <cfg-v2> --candidate <id> [--dedicated] [--dry-run]
python3 -m foundry.local_first_runner screen-exploration  ... --candidate <id> [<id> ...]
python3 -m foundry.local_first_runner compare-exploration ... --candidate <id> [--paths A,L,E] [--screening-campaign <id>]
python3 -m foundry.local_first_runner report --campaign <cfg-v2> --results <results-<campagne>.jsonl>
```

La configuration v2 (schéma `foundry.local-first-campaign.v2`) n'est acceptée que par les modes v2 et inversement (refus, code 2). Le rapport v2 contient `exploration_screening` (table par candidat, rappel moyen de fonctions en premier : rappel moyen de fonctions, précision et rappel moyens de fichiers, durée totale, refus, contaminations, détail par tâche ; candidat retenu ou arrêt) et `exploration_comparison` (bras L et E contre A : trois verdicts, détail de l'économie, localisation de l'explorateur par tâche, décision). Le détail du lanceur est dans [`pat-19-launcher-v1.md`](pat-19-launcher-v1.md), section « Protocole v2 ».

## 11. Limites (le rapport les dira)

- **Plafond de 10 fonctions** : un rapport qui cite plus de 10 fonctions n'est noté, et ne transmet à l'implémenteur, que ses 10 premières ; une bonne 11e fonction est perdue (le prompt demande les plus pertinentes d'abord). C'est une règle gelée, validée avec le reste de la v2.
- **Précision au sens large** : citer le fichier de test réellement modifié par la PR ou le CHANGELOG ne coûte rien à la précision ; l'explorateur peut y gagner en nommant des fichiers que la PR a touchés sans qu'ils soient produit.

- **Bundle inchangé, contrôlé** : le lanceur relève `git status --porcelain` du bundle avant et après chaque exploration (locale et cloud) ; un bundle modifié ou illisible **refuse** l'exploration (score 0, jamais rejouée, rapport non utilisé, `exploration.bundle_modified` consigné). Pour l'explorateur cloud c'est une observation, pas une garantie : la lecture seule n'est pas imposée.
- **Lecture seule du bras cloud E non imposée** : Claude Code ne s'authentifie pas sous `sandbox-exec` ; l'explorateur Haiku est en lecture seule par consigne et par jeu d'outils (ni `Edit` ni `Write`), mais `Bash` reste ouvert (règles de refus de la v1 au mieux, audit après exécution) ; l'essai a observé un bundle inchangé, sans garantie. Les limites d'exposition des bras cloud de la v1 s'appliquent entières à L et E (implémenteur, relecteur, explorateur E).
- **Source du rapport** : les jeux d'outils épinglés n'ont aucun outil d'écriture ; le prompt demande donc le JSON comme message final et le lanceur le lit dans le flux ; un `report.json` écrit par le bras dans son dossier d'essai est aussi accepté. Les noms d'outils d'`omp` et la forme du message final ont été épinglés par l'essai du 2026-10-06.
- **Vérité terrain mince** : chaque tâche modifie un seul fichier produit, parfois 1 à 4 fonctions ; la précision de fichiers ≥ 0,5 sanctionne donc tout rapport qui cite plus de deux fichiers par fichier vrai. C'est la règle validée par le mainteneur, telle quelle.
- **Corpus** : 6 tâches de tamis et 6 de comparaison, non indépendantes (`limits` du manifeste : branche empilée, jumelles, 8 des 12 tâches touchent `tests/test_linear_tracker.py`) ; un échantillon de 6 tâches n'est pas une preuve statistique générale.
- **Rapport non vérifié par le juge de tests** : le tamis ne mesure que la localisation, pas l'effet aval ; seul le coût net par tâche acceptée de la comparaison dit si l'exploration vaut son prix.
- **Un explorateur contaminé en comparaison** laisse le bras indécis (et non compté pour zéro comme au tamis), car on ne peut pas attribuer son effet aval.
- **Ordre des tâches** : les bras A, L, E d'une tâche sont joués à la suite ; un effet de cache côté hôte entre bras n'est pas isolé.

- **Coordonnées du protocole, pas choix du lanceur** : le plafond de 10 fonctions, la correspondance des noms de fonctions (nom qualifié ou dernier composant), la précision 0 d'un rapport sans fichier et la définition de la vérité terrain (produit seulement pour le rappel ; diff pour la précision ; ligne supprimée lue à la base, ligne ajoutée à la fusion ; algorithme myers) déterminent le score ; la définition du travail premium (`premium_work_definition`), le traitement d'un rapport refusé en comparaison (`refused_report_in_comparison`), les bornes de la qualité sur les tâches indécises (`quality_bounds_on_undecided`) et les cas d'économie `unavailable` (`economy_unavailable_cases`) déterminent les verdicts de la section 6 : ce sont des coordonnées du protocole (`exploration.protocol_coordinates` de la configuration) ; en changer une ouvre une **v3**. Seules les limites de rendu du rapport dans l'énoncé (20 fichiers, 1500 caractères de justification) restent des choix du lanceur.
- **Bornes** : une exploration qui atteint `explorer_max_seconds` (même arrêtée par le harnais à `--max-time` sans `timed_out`) est un refus ; un `start_error` (le bras n'a pas tourné) est une panne du lanceur : nulle, rejouée une fois, pas un refus du modèle. Le prompt du bras E annonce le plafond d'étapes « là où le harnais les compte » : le bras cloud n'est pas borné en étapes.
- **Préflight refusé** : si le préflight machine refuse (au tout début de `compare-exploration` quand le bras L est demandé, avant toute dépense cloud, puis avant chaque exploration locale de L), l'opérateur libère la machine et **reprend** par une relance sous le même identifiant de campagne (reprise bornée) ; rien n'est perdu ni rejoué. Un refus après du travail cloud de la même tâche laisse ce travail enregistré. Ni cette reprise, ni celle qui suit une exploration nulle, ni un lancement `--paths L` ne laissent d'avertissement `preflight_without_attempt` au registre (le préflight de départ suivi d'un autre préflight du même lancement n'est pas un trou).
- **`main` et les configurations v1** : le chargement d'une configuration en erreur sort désormais en code 2 avec un message, sans trace, y compris pour une configuration v1 (changement de comportement limité à ce cas d'erreur).
- **Campagne de comparaison interrompue** : le rapport de comparaison ne lit pas les arrêts. Une tâche des bras L ou E qui n'a que son enregistrement d'exploration (coupure entre l'exploration et la réservation de l'implémenteur) n'est **pas** comptée comme refusée : elle est indécise (`awaiting_implementer` du bras), la campagne est `incomplete_campaign` et rien n'est conclu. Une reprise sous le même identifiant de campagne joue l'implémenteur manquant. Plus généralement, un rapport lu avant la reprise d'une campagne interrompue ne vaut pas conclusion.
- **Liste d'autorisation système réduite, mesurée une seule fois pour de vrai** : la liste réduite (fixée le 2026-10-07, après la mesure réelle de la section 8) n'a pas encore été mesurée pour de vrai : elle ne le sera que par le premier préflight réel du tamis. Consigne de l'opérateur : le coordinateur lance `preflight --dedicated` et lit son résultat **avant** de lancer le tamis.
- **Chemins du lanceur jamais joués avec de vrais pilotes** : les essais réels sur le dépôt jouet sont passés par `execute_driver`, pas par `Runner.explore_local` ni `_explore_step_cloud` ; l'audit de contamination, le contrôle `git status` du bundle et la normalisation des chemins du rapport tournent donc pour la première fois avec de vrais pilotes à la première tentative du tamis. Consigne de l'opérateur : **inspecter l'enregistrement de cette première tentative** (contamination, `exploration.bundle_modified`, source et chemins du rapport, score) avant de continuer.
- **Vérité terrain et CI** : le test qui recalcule la vérité terrain depuis les vrais diffs est ignoré, avec un message, dans un clone sans historique ; la preuve « testé sur ces diffs » repose alors sur l'exécution dans un clone complet (faite le 2026-10-06) et sur le sha256 du fichier gelé, vérifié à chaque lancement.
- **Prompt final essayé en réel** : après l'ajout au prompt de l'annonce des bornes et du plafond de 10 fonctions, les deux explorateurs ont été réessayés sur le dépôt jouet le 2026-10-07 avec le texte gelé (`final_prompt_trial` de `pat-19-preflight-v2-2026-10-06.json`) : rapport lu, score jouet 1,0 / 1,0 / 1,0 pour les deux, bundle inchangé.
- **Correspondance des noms de fonctions** : un nom rapporté sans classe (`update`) correspond à toute méthode du même fichier qui porte ce nom (`A.update` et `B.update`) ; effet faible avec 1 à 4 fonctions vraies par tâche.
